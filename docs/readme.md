# readme — README как презентация проекта

Собирает и проверяет README так, чтобы новый посетитель за минуту понял: что это, для кого, что умеет и как попробовать.
Берёт только подтверждённое: факты `scan`, проверенные утверждения `claims.json`, примеры и команды из самого репозитория,
медиа с известным происхождением и слова автора. Текста от себя не добавляет: чего нет — остаётся пустым местом
с пометкой и попадает в список «для человека». По умолчанию README пишется на русском.

Порядок работы: **план → черновик → проверка → запись**.

## Команды

| Команда | Что делает |
|---|---|
| `readme layout [--style …]` | определяет тип проекта и планирует структуру → `.repokit/readme.layout.json` |
| `readme human` | шаблон полей автора → `.repokit/readme.human.yaml` |
| `readme plan` (то же: `readme generate`) | черновик → `.repokit/readme.draft.md`, состояние каждого раздела, список «для человека» |
| `readme audit [--draft] [--fix]` | проверка по восьми категориям → `.repokit/readme.audit.json`; код 1 при обязательных замечаниях |
| `readme hero-check [--draft]` | только первый экран: что это, для кого, что делать дальше |
| `readme apply [--dry-run] [--regenerate]` | записывает `README.md`; `--dry-run` показывает diff и ничего не меняет |
| `readme verify-quickstart` | выполняет команды запуска из README во временной копии; см. [verify](verify.md) |
| `readme check` | незаполненные места, битые ссылки, alt-тексты; код 1 при проблемах |
| `readme presets` | фиксированные шаблоны для `--preset` |
| `examples extract` | реальные примеры использования → `.repokit/examples.json` |
| `diagram architecture [--max-blocks 8]` | схема Mermaid по коду → `.repokit/architecture.mmd` |

Общие флаги `plan`, `layout`, `apply`: `--style`, `--preset`, `--lang ru|en`, `--hero <файл>`, `--hero-dark <файл>`, `--banner <файл>`.
Выбор запоминается в `.repokit/readme.options.json`.

## Тип проекта

README библиотеки и README веб-приложения устроены по-разному, поэтому сначала определяется тип проекта.
Каждое решение опирается на факты, перечисленные в поле `signals` (файл, зависимость, точка входа):

| Тип | Что в начале | Обязательные разделы |
|---|---|---|
| `web-app` | скриншот или GIF главного сценария | главное изображение, возможности, быстрый старт |
| `cli` | установка и пример команды | быстрый старт, пример, команды |
| `library` | минимальный пример кода | быстрый старт, пример использования |
| `sdk` | минимальный пример кода | быстрый старт, пример использования, настройка |
| `api` | запуск и список эндпоинтов | быстрый старт, API, настройка |
| `ai-agent` | что умеет и что ему нужно для работы | возможности, быстрый старт, настройка, пример |
| `mobile-app`, `desktop-app`, `game` | скриншоты | главное изображение, возможности, быстрый старт |
| `ml-research` | суть и как воспроизвести | быстрый старт, пример |
| `dev-tool` | установка и пример | быстрый старт, пример |
| `template` | что внутри и как начать | возможности, быстрый старт |
| `monorepo` | список пакетов | пакеты, быстрый старт |
| `infrastructure` | что разворачивает и что для этого нужно | архитектура, быстрый старт, настройка |

Это не жёсткие шаблоны. Раздел попадает в README, только если ему есть что показать: «Настройка» — если код читает
переменные окружения, «Команды» — если найдены определения командной строки, «Архитектура» — если связанных модулей
не меньше трёх. Причина каждого решения записана в плане. Если уверенность ниже 60 %, тип просит подтвердить человека.

## План README

`readme layout` пишет `.repokit/readme.layout.json` ([схема](../schemas/readme-layout.schema.json)):

```json
{
  "projectType": "cli",
  "style": "developer",
  "audience": ["разработчики", "пользователи терминала"],
  "primaryAction": "install",
  "hero": false,
  "demo": "terminal",
  "architectureDiagram": false,
  "quickStart": true,
  "usageExamples": true,
  "comparisonTable": false,
  "sections": [
    { "id": "quickstart", "priority": "must", "reason": "…" },
    { "id": "configuration", "priority": "omit", "reason": "код не читает переменных окружения" }
  ],
  "mode": "generate"
}
```

Приоритет раздела: `must` — без него README не отвечает на главный вопрос; `should` — полезно большинству;
`optional` — по желанию; `omit` — рассмотрен и исключён, причина указана.
Файл можно править: `plan` и `apply` берут из него тип проекта и список разделов, пока стиль тот же.
`comparisonTable` всегда `false`: для сравнения нужны факты о других проектах, а их в репозитории нет.

## Стили

| Стиль | Что оставляет |
|---|---|
| `minimal` | только разделы `must` |
| `developer` | `must` и `should`; установка, пример и команды раньше картинок |
| `product` | `must` и `should`; шапка по центру, упор на то, что видит пользователь |
| `showcase` | всё, включая `optional`; крупное демо в начале |
| `research` | `must` и `should`; суть, воспроизведение, результаты |
| `docs` | всё; длинные разделы свёрнуты в `<details>` |

Без `--style` стиль выбирается по типу проекта.

## Откуда берётся каждый раздел

| Раздел | Источник | Если данных нет |
|---|---|---|
| Шапка | название, тэглайн автора, строка ссылок (демо · документация · быстрый старт — только существующие), проверяемые бейджи | пометка «не заполнено» |
| Главное изображение | файл из `--hero` — GIF из `studio`, скриншот из `capture screenshot` или запись терминала из `capture terminal`; `<picture>` при наличии тёмного варианта | пометка; файл не из `capture`/`studio` — предупреждение |
| Проблема, Решение | поля `problem`, `solution`; раздел появляется, только если автор их заполнил | — |
| Возможности | утверждения `implemented` и `partial` с доказательством; каждое со ссылкой на строки кода | пометка |
| Пакеты | манифесты пакетов монорепозитория: имя, описание | раздел опускается |
| Быстрый старт | `git clone`, команды установки, запуска и тестов из `scan`; напоминание об обязательных переменных окружения | пометка |
| Пример использования | лучший пример из `examples extract`, дословно, со ссылкой на файл и строки | пометка: пример не сочиняется |
| Команды или Опции | подкоманды и опции из `argparse`, `click`, `commander`, `cobra`, `clap`; таблица от трёх строк, иначе список | раздел опускается |
| Настройка | переменные окружения, которые читает код, с местом чтения и признаком обязательности; значения не читаются | раздел опускается |
| Архитектура | схема Mermaid по импортам и обращениям к API, не больше восьми блоков | раздел опускается |
| API и страницы | роуты из `scan` | раздел опускается |
| Технологии | бейджи только для найденного в зависимостях и файлах | раздел опускается |
| Демо | поля `demoUrl`, `videoUrl`, адрес проверенного деплоя | раздел опускается |
| Для жюри | критерии из `brief.json`; только при наличии разбора правил | раздел опускается |
| Ограничения и планы | заглушки, частичные реализации, отсутствие тестов, поле `roadmap` | раздел опускается или пометка |
| Команда | поле `team` | раздел опускается |
| Лицензия | файл лицензии | пометка: лицензию выбирает человек |

## Примеры

`examples extract` ищет примеры в трёх местах, от лучшего к худшему: небольшие файлы в `examples/`, блоки кода под заголовками
вроде «Usage» в README и `docs/`, короткие тесты. Код копируется дословно; у каждого примера есть файл, строки и хеш этих строк.
Папка внутри `examples/` со своим манифестом, README или тестами считается отдельным учебным проектом, а не примером.

Если примеров нет, раздел остаётся с пометкой: придуманный пример мог бы не работать.
Проверить, что пример запускается, — задача автора или `verify run --exec`.

## Схема архитектуры

`diagram architecture` строит схему из импортов и обращений клиента к роутам. Файлы сворачиваются в папки, пока блоков не станет
не больше восьми; в монорепозитории блоки — пакеты, стрелки — импорты между ними. Стрелки, которой нет в коде, на схеме не будет.
Если связанных модулей меньше трёх, команда советует схему не ставить.

## Аудит

`readme audit` не ставит оценку. Каждая строка — отдельная проверка, пройденная или нет:

```
Понятность
  ✓ есть название
  ✗ описание начинается общей фразой — начните с того, что проект делает
Первый экран
  ✓ бейджей в начале: 3
Быстрый старт
  ✗ код читает переменные окружения, о которых README молчит: API_KEY (src/config.ts:4)
```

| Категория | Что проверяется |
|---|---|
| Понятность | название; описание в начале, его длина и первые слова; рекламные слова без содержания |
| Первый экран | сколько строк до первого раздела; число бейджей; изображение у проектов с интерфейсом; понятное следующее действие; оглавление не раньше описания |
| Визуалы | есть ли изображения и демо в движении там, где они нужны; вес файлов; alt-тексты; прозрачные PNG, которые не видны в одной из тем |
| Быстрый старт | раздел о запуске, блоки с командами, переменные окружения из кода, `.env.example` |
| Примеры | пример использования у библиотек, CLI, API и инструментов; есть ли в README примеры, уже лежащие в репозитории |
| Утверждения | «молниеносно», «production-ready», «100% secure» и подобное без числа или ссылки рядом; устаревшие доказательства `claims.json` |
| Оформление | один H1, порядок уровней заголовков, число разделов и строк, эмодзи в заголовках, таблицы из одной-двух строк и шире шести колонок, абзацы длиннее 120 слов, блоки кода длиннее 60 строк вне `<details>` |
| Файлы | битые ссылки, незаполненные места, неиспользуемые медиафайлы, имена с пробелами и заглавными буквами |

Замечание с пометкой «обязательное» (`severity: error`) даёт код выхода 1; остальные — советы.
Пороги взяты из разбора 25 ухоженных README: медиана — три бейджа в начале, около 160 строк и шесть разделов;
эмодзи в заголовках не встретились ни разу.

`--fix` делает только механические правки, которые не меняют смысл: второй заголовок первого уровня понижается,
перескоки уровней заголовков выравниваются, блоки кода длиннее 60 строк сворачиваются в `<details>`, лишние пустые строки убираются.
Прежняя версия сохраняется в `.repokit/readme.backup.md`; `--fix --dry-run` только показывает список правок.
Формулировки не трогаются: текст правит автор или Claude, по замечаниям. Вес, уборку и имена медиа исправляет [`assets`](assets.md).

## Существующий README

Написанное автором важнее шаблона.

- Если в README не меньше 60 непустых строк и четырёх разделов, план получает `mode: "improve"`, а `readme apply` останавливается
  с кодом 3. Дальше два пути: править существующий текст по замечаниям `readme audit` или явно заменить его — `readme apply --regenerate`.
- README, который записал сам repokit, перезаписывается без вопроса.
- При замене прежняя версия сохраняется в `.repokit/readme.backup.md`.
- Собственные разделы автора (заголовки второго уровня, которых нет среди генерируемых) переносятся без изменений и ставятся перед лицензией.
- Если раздел автора похож на дубль «Быстрого старта», он сохраняется, а в списке «для человека» появляется просьба оставить один вариант.

Повторный `apply` без изменений в фактах ничего не меняет.

## Правила текста

- Первое предложение говорит, что проект делает, а не что он «мощный» или «современный».
- Измеримое качество (скорость, зрелость, безопасность) упоминается только с числом или ссылкой на замер.
- Утверждение без доказательства, со статусом `unverified`, или чей код изменился после фиксации, в README не попадает.
- Заглушка (`mock`) выводится только в «Ограничениях».
- Бейджей со звёздами, скачиваниями и прочими непроверяемыми числами нет.
- Таблица — от трёх строк; две записи читаются лучше списком.
- Длинные справочные разделы сворачиваются в `<details>`; то, без чего нельзя запустить проект, не сворачивается никогда.

## Фиксированные шаблоны

`--preset compact | showcase | technical` включает прежнее поведение: порядок разделов задаёт `presets/readme/<имя>/template.md`,
тип проекта не учитывается. `showcase` и `technical` рассчитаны на подачу на хакатон и содержат раздел «Для жюри».
Заголовки и служебные фразы лежат в `presets/readme/_i18n/ru.yaml` и `en.yaml`.

## Технологии

```markdown
![Python](https://img.shields.io/badge/Python-3670A0?style=for-the-badge&logo=python&logoColor=ffdd54)
```

repokit знает около сорока технологий и показывает только те, для которых в репозитории есть основание.
Чего не нашлось автоматически, автор добавляет полем `stack` в `.repokit/readme.human.yaml`; в плане появится предупреждение,
что технология не подтверждена зависимостями или файлами проекта. Бейджи — картинки с shields.io: их загружает браузер читателя.

## Особенность GitHub

Тег `<video>` в README работает только со ссылкой, которую GitHub выдаёт при перетаскивании файла в веб-редактор.
Поэтому главным медиа служит GIF или WebP, а ссылку на видео автор добавляет в поле `videoUrl` сам.
