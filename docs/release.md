# release — релиз на GitHub

Собирает описание релиза из фактов о проекте и создаёт релиз через ваш `gh` — если релиза с таким тегом ещё нет.

```bash
node packages/cli/dist/bin.js release plan --repo examples/web-app
```

| Команда | Что делает |
|---|---|
| `release plan [--tag v1.0.0]` | описание релиза → `.repokit/release.md`; его можно править |
| `release create --confirm [--draft] [--tag …]` | создаёт релиз; без `--confirm` — код 3 |

## Что попадает в описание

- вступление — тэглайн из полей автора;
- «Что работает» — только утверждения, подтверждённые кодом;
- «Известные ограничения» — заглушки и частично сделанное, теми же словами, что в README;
- «Как запустить» — команды из `scan`;
- технологии и ссылка на работающую версию (если `deploy check` её подтвердил).

К релизу прикладываются файлы, если они есть: `docs/media/hero.mp4`, `hero.webm`, `hero-3d.mp4`, `how-it-works.mp4`,
`banner.png`, `docs/slides/slides.pdf`.

Тег по умолчанию берётся из версии в `package.json` или `pyproject.toml`; если версия нигде не объявлена — `v0.1.0`
с просьбой задать свой.

## Создание

`release create --confirm`:

1. проверяет, что у репозитория есть origin на GitHub и что вы вошли в `gh` (иначе код 3 и команда для вас);
2. смотрит, есть ли уже релиз с этим тегом — если есть, ничего не делает;
3. выполняет `gh release create` с описанием из `.repokit/release.md` и файлами.

Релиз виден всем и рассылает уведомления подписчикам, поэтому без `--confirm` он не создаётся. `--draft` создаёт черновик.
GitHub привязывает тег к тому, что уже запушено: если последний коммит не отправлен, будет предупреждение.

Создание релиза проверено тестами с подставным исполнителем команд; настоящий релиз при разработке не создавался.
