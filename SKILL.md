# repokit

Набор CLI-сервисов. Они дают факты и проверки; формулировки и решения — твои и пользователя.
Сервисы не вызывают LLM и не ходят в сеть без явного флага.

Запуск из корня repokit: `node packages/cli/dist/bin.js <сервис> <команда>` (перед первым запуском `pnpm install && pnpm build`).
Ниже для краткости — `repokit`.

## Правила, которые нельзя нарушать

1. **Только правда.** В README попадает только то, что подтверждено кодом (`claims.json`, статус `implemented` или `partial` с доказательством). Заглушки и недоделки идут в «Limitations & Roadmap».
2. **Не обманывать оценщиков.** Никаких скрытых инструкций для LLM-ревьюеров, невидимого текста, комментариев, которые врут о коде, накрутки коммитов, переписывания истории git.
3. **Секреты не печатаются и не коммитятся.** Не читай `.env` вслух, не вставляй токены в команды. Нужен логин — остановись и попроси пользователя.
4. **Человек решает.** Правки кода — патчем на одобрение. Деплой, пуш, публикация — только после явного «да».
5. **Код выхода 3** означает «нужен человек»: покажи пользователю, что требуется, и жди.

## Контракт

- `--json` — ровно один JSON-документ в stdout (конверт: `ok`, `exitCode`, `data`, `warnings`, `humanTodo`, `artifacts`). Человеческий текст — в stderr.
- `--dry-run` — ничего не записывать. `--repo <path>` — целевой репозиторий (по умолчанию текущая папка).
- Коды выхода: `0` ок · `1` проверка не пройдена · `2` ошибка использования · `3` нужен человек.
- Артефакты лежат в `.repokit/` целевого репозитория. `humanTodo` из каждого ответа собирай и в конце покажи пользователю одним списком.

## Что доступно сейчас (вехи M1–M2)

| Команда | Что делает |
|---|---|
| `repokit doctor` | проверяет git, ffmpeg, gh, python; ничего не ставит |
| `repokit scan init` | создаёт `.repokit/`; `--write-gitignore` добавляет его в `.gitignore` |
| `repokit scan audit` | факты о проекте → `.repokit/scan.json`: тип, стек, команды запуска, точки входа, роуты, модели, заглушки, замечания |
| `repokit scan context` | выжимка репозитория → `.repokit/context.md` |
| `repokit scan topics` | предлагает GitHub topics (не применяет) |
| `repokit scan claims extract` | утверждения из раздела Features/«Возможности» README → `.repokit/claims.json`, все со статусом `unverified` |
| `repokit scan claims pin` | фиксирует хэши строк-доказательств |
| `repokit scan claims check` | проверяет доказательства; exit 1, если что-то не подтверждено или код изменился |

| `repokit capture scenario draft` | каркас сценария демо из `scan` → `.repokit/capture/scenario.draft.yaml` |
| `repokit capture scenario validate --scenario f` | проверка сценария, список нужных переменных окружения |
| `repokit capture run --scenario f` | запись: `video.mp4`, `events.json`, скриншоты по меткам |
| `repokit capture shots --scenario f --sizes … --themes …` | скриншоты в разных размерах и темах |
| `repokit studio styles` | стили оформления: `light`, `dark`, `glass` |
| `repokit studio render --out docs/media/hero.mp4 --gif` | монтаж последней записи с авто-зумом; GIF ≤ 8 МБ |

Подробности: `docs/scan.md`, `docs/capture.md`, `docs/studio.md`.

Ещё не реализованы (вызов вернёт exit 2): 3D-пресеты `studio` (M3), `brief`, `readme`, `preview` (M4), `verify`, `run` (M5), `deploy` (M6), `polish` (M7).

## Рабочий процесс (доступная часть)

1. `repokit doctor`, затем `repokit scan init --dry-run` — покажи пользователю, что будет создано.
2. `repokit scan audit --json` — прочитай `data`. Записи с `confidence` ниже 0.6 перепроверь, открыв файл.
3. `repokit scan context` — прочитай `.repokit/context.md`, затем сами ключевые файлы из `keyFiles`.
4. `repokit scan claims extract` — получи утверждения README.
5. Для каждого утверждения найди код, который его реализует, и отредактируй `.repokit/claims.json`:
   - реализовано → `status: "implemented"`, `evidence: [{ "file": "app/main.py", "lines": [41, 43] }]`;
   - реализовано частично → `partial` + `note`, чего не хватает;
   - за утверждением стоит заглушка из `scan.mocks` → `mock`;
   - кода не нашёл → оставь `unverified`. Не подбирай «похожие» строки.
   Можно добавлять свои утверждения (`source: "claude"`) о том, что реально есть в коде, но не упомянуто в README.
6. `repokit scan claims pin`, затем `repokit scan claims check`. Exit 1 — исправь `claims.json`, а не ослабляй проверку.
7. Отчитайся пользователю: что подтверждено, что оказалось заглушкой, что не найдено, и список `humanTodo`.

### Демо

8. `repokit capture scenario draft` даёт каркас. Допиши шаги, **прочитав код интерфейса** (селекторы бери из реальной разметки), и сохрани сценарий в репозитории, например `demo.scenario.yaml`.
   - Показывай только то, что в `claims.json` имеет статус `implemented` или `partial`. Заглушку можно показать только с пометкой в самом интерфейсе или с `demoData: true`.
   - Логин — только тестовым аккаунтом; пароль и `storageState` — через `${env:ИМЯ}`. Всё, где виден секрет, добавь в `mask`.
   - Никогда не правь приложение ради красивого кадра и не подменяй его ответы.
9. Покажи сценарий пользователю и получи одобрение. Затем `capture scenario validate` и `capture run`.
10. Посмотри скриншоты из `shots/` — убедись, что в кадре нет секретов и личных данных. Если есть — добавь маску и перезапиши.
11. `repokit studio render --out docs/media/hero.mp4 --gif --dry-run`, затем без `--dry-run`. Предупреждение «происхождение неизвестно» означает, что источник не из `capture` — не используй такой файл в README без объяснения пользователю.
12. Открой постер `hero.png` и проверь результат глазами, прежде чем предлагать его пользователю.

## Чек-лист «человеку»

Эти решения всегда остаются за пользователем — не принимай их сам:

- сценарий демо: что именно показывать и с какими данными;
- тестовый аккаунт и переменные окружения для входа;
- применима ли к пользователю бесплатная лицензия Remotion (частное лицо, НКО или компания до 3 человек);
- лицензия проекта, состав команды, тэглайн и формулировка проблемы;
- что делать с утверждениями README, которые не подтвердились (убрать, доделать, перенести в Roadmap);
- GitHub topics и описание репозитория;
- любые коммиты, пуш и деплой.
