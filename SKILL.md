# repokit

Набор CLI-сервисов. Они дают факты и проверки; формулировки и решения — твои и пользователя.
Сервисы не вызывают LLM и не ходят в сеть без явного флага.

Запуск из корня repokit: `node packages/cli/dist/bin.js <сервис> <команда>` (перед первым запуском `pnpm install && pnpm build`).
Ниже для краткости — `repokit`.

## Правила, которые нельзя нарушать

1. **Только правда.** В README попадает только то, что подтверждено кодом (`claims.json`, статус `implemented` или `partial` с доказательством). Заглушки и недоделки идут в «Limitations & Roadmap».
2. **Не обманывать оценщиков.** Никаких скрытых инструкций для LLM-ревьюеров, невидимого текста, комментариев, которые врут о коде, накрутки коммитов, переписывания истории git.
3. **Секреты не печатаются и не коммитятся.** Не читай `.env` вслух, не вставляй токены в команды. Нужен логин — остановись и попроси пользователя.
4. **Человек решает.** Правки кода — патчем на одобрение. Деплой, пуш, публикация — только после явного «да».
5. **Код выхода 3** означает «нужен человек»: покажи пользователю, что требуется, и жди.

## Контракт

- `--json` — ровно один JSON-документ в stdout (конверт: `ok`, `exitCode`, `data`, `warnings`, `humanTodo`, `artifacts`). Человеческий текст — в stderr.
- `--dry-run` — ничего не записывать. `--repo <path>` — целевой репозиторий (по умолчанию текущая папка).
- Коды выхода: `0` ок · `1` проверка не пройдена · `2` ошибка использования · `3` нужен человек.
- Артефакты лежат в `.repokit/` целевого репозитория. `humanTodo` из каждого ответа собирай и в конце покажи пользователю одним списком.

## Рабочий процесс (доступная часть)

1. `repokit doctor`, затем `repokit scan init --dry-run` — покажи пользователю, что будет создано.
2. `repokit scan audit --json` — прочитай `data`. Записи с `confidence` ниже 0.6 перепроверь, открыв файл.
3. `repokit scan context` — прочитай `.repokit/context.md`, затем сами ключевые файлы из `keyFiles`.
4. `repokit scan claims extract` — получи утверждения README.
5. Для каждого утверждения найди код, который его реализует, и отредактируй `.repokit/claims.json`:
   - реализовано → `status: "implemented"`, `evidence: [{ "file": "app/main.py", "lines": [41, 43] }]`;
   - реализовано частично → `partial` + `note`, чего не хватает;
   - за утверждением стоит заглушка из `scan.mocks` → `mock`;
   - кода не нашёл → оставь `unverified`. Не подбирай «похожие» строки.
   Можно добавлять свои утверждения (`source: "claude"`) о том, что реально есть в коде, но не упомянуто в README.
6. `repokit scan claims pin`, затем `repokit scan claims check`. Exit 1 — исправь `claims.json`, а не ослабляй проверку.
7. Отчитайся пользователю: что подтверждено, что оказалось заглушкой, что не найдено, и список `humanTodo`.

### Демо

8. `repokit capture scenario draft` даёт каркас. Допиши шаги, **прочитав код интерфейса** (селекторы бери из реальной разметки), и сохрани сценарий в репозитории, например `demo.scenario.yaml`.
   - Показывай только то, что в `claims.json` имеет статус `implemented` или `partial`. Заглушку можно показать только с пометкой в самом интерфейсе или с `demoData: true`.
   - Логин — только тестовым аккаунтом; пароль и `storageState` — через `${env:ИМЯ}`. Всё, где виден секрет, добавь в `mask`.
   - Никогда не правь приложение ради красивого кадра и не подменяй его ответы.
9. Покажи сценарий пользователю и получи одобрение. Затем `capture scenario validate` и `capture run`.
10. Посмотри скриншоты из `shots/` — убедись, что в кадре нет секретов и личных данных. Если есть — добавь маску и перезапиши.
11. `repokit studio render --out docs/media/hero.mp4 --gif --dry-run`, затем без `--dry-run`. Предупреждение «происхождение неизвестно» означает, что источник не из `capture` — не используй такой файл в README без объяснения пользователю.
12. Открой постер `hero.png` и проверь результат глазами, прежде чем предлагать его пользователю.
13. Для 3D-подачи: `studio presets list`, выбери пресет по пропорциям слота (десктопная запись → `laptop-orbit` или `browser-tilt`, мобильный скриншот → `phone-float`). В слот клади только файлы из `capture`. Сначала `studio still` на один кадр, потом `studio render --preset`.
    - Предупреждение о пропорциях означает обрезку краёв: проверь по кадру, что важное не срезано, или сними запись с подходящим `viewport` (для 16:10 — например 1280×800).
    - Без GPU добавь `--gl swangle`.

### Режиссёрская сцена — когда нужна своя постановка

Полное описание полей — `docs/scenes.md`. Работай циклом «правка → один кадр → смотри»:

- `studio scene init` даёт рабочую сцену с авто-камерой. Дальше правь JSON: `objects[].position/rotation/scale/keyframes` двигают устройство, `camera.keyframes[].focus` ведёт камеру (`point` — CSS-пиксели страницы, `zoom` 1 = экран целиком, `yaw`/`pitch` — угол), `effects` ставит подъём элемента, искры и кольца.
- Координаты кликов и рамки элементов бери из `events.json` (поля `x`, `y`, `box`), моменты времени — из поля `t`.
- После каждой правки: `studio still --scene f --at <сек>` и **открой PNG**. Не рендерь весь ролик, пока кадры в ключевые моменты не выглядят как надо.
- На экранах — только записи из `capture`. В `captions` пиши только то, что в этот момент видно на экране.
- Карточки (`cards`) и связи (`links`) — для схем и пояснений. `studio explain` строит разбор из кода; дополняя его, называй в карточках и подписях только те модули, роуты и сервисы, которые нашёл в исходниках (проверь по `scan.json` и самим файлам). Не рисуй связь, которой в коде нет.
- Музыку не выбирай сам: `--music` — только файл, который дал пользователь.
- `release create --confirm` — только после явного согласия пользователя: релиз публичен.

### README

Цель — чтобы новый посетитель за минуту понял, что это за проект, для кого он, что умеет и как его попробовать.
Красота README — это структура, текст, настоящие скриншоты и рабочие примеры, а не количество украшений.

- **Сначала план.** `readme layout --json`: проверь `projectType` по `signals` (при `confidence` ниже 0.6 — открой код и спроси пользователя), прочитай причины у разделов. Не согласен с планом — правь `.repokit/readme.layout.json` (`priority`: `must`, `should`, `optional`, `omit`), а не обходи его.
- **Существующий README важнее шаблона.** При `mode: "improve"` не заменяй README: запусти `readme audit`, возьми замечания и правь текст точечно — сохраняй хорошее, сокращай лишнее, переставляй разделы, дополняй недостающее. `readme apply --regenerate` — только если пользователь сам попросил написать README заново.
- **Первый экран.** `readme hero-check`: название, одно-два предложения о том, что проект делает и для кого, понятное следующее действие, не больше шести бейджей, у проектов с интерфейсом — настоящее изображение.
- **Текст.** Начинай с того, что проект делает. Не пиши «мощный», «революционный», «нового поколения», «бесшовный»; «быстрый», «production-ready», «безопасный» — только рядом с числом или ссылкой на замер. Не объясняй очевидное, не повторяй одно и то же в разных разделах.
- **Примеры — только настоящие.** `examples extract` даёт код с файлом и строками. Не сочиняй пример: если подходящего нет, предложи пользователю добавить файл в `examples/` и убедись, что он запускается.
- **Визуалы по делу.** Веб, мобильное, десктоп, игра — один-три скриншота или GIF главного сценария из `capture`. CLI — `capture terminal` с командой, которую пользователь запустил бы первой; команду согласуй с пользователем (она выполняется на его машине) и не подбирай запуск ради красивого вывода. Библиотеке и SDK картинка не нужна — нужен пример кода. Схему (`diagram architecture`) ставь, только если она помогает понять систему; меньше трёх блоков — не ставь.
- **Не перегружай.** Таблица — от трёх строк. Длинные справочные разделы — в `<details>`; установку и запуск не сворачивай никогда. Раздел без содержания не добавляй ради полноты.
- **После правок** — `readme audit` снова (механику исправит `--fix`), затем `assets check`. `readme verify-quickstart` запускает чужие команды — спроси пользователя. Замечания устраняй в тексте и файлах, а не ослабляй проверку.

### Правила хакатона (если проект сдаётся на хакатон)

14. Есть правила хакатона → `brief extract`, затем заполни `.repokit/brief.json` **строго по тексту** `.repokit/brief.source.txt`: у каждого критерия, требования, срока и ограничения — дословная `quote`. Не добавляй критерии «от себя». Правил нет → `brief init --default` и скажи пользователю, что это допущение. Потом `brief validate`.
15. В `claims.json` добавь утверждениям `criteria: [id]` — какие критерии они подтверждают.
16. `readme human`, затем **спроси пользователя** про тэглайн, проблему, решение, команду. Можешь предложить формулировки, но в `.repokit/readme.human.yaml` записывай только то, что он подтвердил. Проще дать ему `preview serve --open` — там форма.
17. Раздел «Технологии» собирается сам — из зависимостей и файлов. Не добавляй в `stack` то, чем проект не пользуется.
    `readme plan --hero docs/media/hero.gif`. Прочитай состояние разделов: «ПУСТО» означает, что нужны данные, а не что их надо придумать.
18. `preview shot`, открой PNG и посмотри README глазами оценщика; `preview check --json` покажет, что на первом экране, что не загрузилось, что шире колонки.
19. `readme audit --draft` — проверь черновик до записи. Покажи пользователю `readme apply --dry-run` (или интерфейс). Записывай `readme apply` только после его «да». После — `readme audit` и `readme check`.
    - Пометки `<!-- FILL -->` не удаляй вручную и не заполняй выдумкой: это список того, что решает человек.
    - Не добавляй в README ничего в обход `claims.json`.

### Проверка и сквозной прогон

20. `repokit verify run --source worktree` перед коммитом, `repokit verify run` после. Ошибку устраняй в источнике (уберите секрет, почините ссылку), а не обходи проверку. `--exec` и `--online` запускают чужие команды и ходят в сеть — спроси пользователя.
    - Найденный секрет недостаточно удалить из файла: скажи пользователю, что ключ нужно отозвать.
21. Вместо шагов 1–20 по отдельности можно вести `repokit run <путь>`: он остановится с кодом 3 и скажет, что нужно. Твоя часть — разметить `brief.json` и `claims.json`, написать сценарий демо. `--approve demo` и `--approve readme` передавай **только после явного согласия пользователя** на каждый шаг.

### Деплой

22. `deploy detect`, затем `deploy plan`: покажи пользователю площадку, ограничения бесплатного тарифа и что придётся сделать ему самому. Выбор площадки — его.
23. `deploy apply --dry-run` → покажи файлы → `deploy apply`. Это правка репозитория: коммитит и пушит пользователь (или ты по его явной просьбе).
24. `deploy run --confirm` передавай **только после явного «да, публикуй»**: это выкладывает проект в интернет. Код 3 значит «нужен вход» — передай пользователю команду входа дословно и жди. Никогда не логинься сам, не проси и не вводи токены и пароли.
    - Значения переменных окружения задаёт пользователь в панели площадки. Не читай `.env`, не вставляй значения в команды и файлы.
25. `deploy check --url <адрес>`. Если сайт не отвечает — не пиши ссылку в README вручную. После успешной проверки `readme plan` сам добавит её в раздел «Демо».

## Чек-лист «человеку»

Эти решения всегда остаются за пользователем — не принимай их сам:

- сценарий демо: что именно показывать и с какими данными;
- тестовый аккаунт и переменные окружения для входа;
- применима ли к пользователю бесплатная лицензия Remotion (частное лицо, НКО или компания до 3 человек);
- на какую площадку деплоить и публиковать ли проект вообще; вход в её CLI; значения секретов;
- лицензия проекта, состав команды, тэглайн и формулировка проблемы;
- заменять ли существующий README целиком (`--regenerate`) или править его;
- удаление и переименование медиафайлов (`assets prune`, `assets normalize`);
- что делать с утверждениями README, которые не подтвердились (убрать, доделать, перенести в Roadmap);
- GitHub topics и описание репозитория;
- любые коммиты, пуш и деплой.
